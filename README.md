# crypto-market-rag

A Retrieval-Augmented Generation (RAG) system that answers questions about the crypto market by combining **semantic search** (news, coin descriptions) with **exact structured data** (live prices), then generates grounded, natural-language answers — without inventing numbers.

> **What this means in plain terms:** ask it "how is Bitcoin doing today?" and it retrieves the actual current price from the database, pulls relevant recent news, and writes a natural summary — the price is never guessed by the AI, only the writing is.

---

## Why this project exists

Most "AI chatbot for X data" demos have a credibility problem: the language model can silently invent plausible-sounding numbers. This project is built around one rule, enforced structurally rather than just requested in a prompt: **any number that ends up in an answer is computed in SQL, never generated by the LLM.** The LLM only ever writes the narrative around numbers it's handed.

This matters for anyone considering AI-assisted tools for financial or operational decisions — a wrong-but-confident-sounding number is worse than no answer at all.

---

## How it relates to `crypto-market-pipeline`

This project is **not standalone** — it's an additional capability layered on top of an existing data engineering pipeline, [`crypto-market-pipeline`](../crypto-market-pipeline), which handles the "boring but essential" data engineering work: pulling live and historical prices from CoinGecko, validating and transforming them (PySpark), and loading them into PostgreSQL on a schedule (Airflow).

```
crypto-market-pipeline                    crypto-market-rag
(pure data engineering)                   (RAG + AI layer)
┌─────────────────────┐                   ┌─────────────────────┐
│ CoinGecko API        │                   │ CoinTelegraph RSS    │
│      ↓                │                   │      ↓                │
│ PySpark transform     │                   │ chunk + embed         │
│      ↓                │                   │      ↓                │
│ dim_coins             │──── read-only ───▶│ rag.documents         │
│ fact_coin_prices       │    (network)      │ (pgvector)            │
└─────────────────────┘                   └─────────────────────┘
        │                                          │
        └──────────── same Postgres ───────────────┘
        (crypto_postgres, shared via crypto_shared_net)
```

**Deliberately separate, on purpose:** the two projects have their own Docker images, their own Airflow instances, and their own repos. Early on, this project's DAGs were run inside the pipeline's Airflow container to save setup time — but that polluted the pipeline's dependencies with AI-specific libraries and blurred its "pure data engineering" story. The current setup restores that separation: this project connects to the pipeline's PostgreSQL over a shared Docker network, as a read-only consumer, and owns its own orchestration entirely.

`crypto-market-rag` never writes to the pipeline's tables (`dim_coins`, `fact_coin_prices`) — it only reads from them, through a dedicated least-privilege database role (`rag_user`).

## Architecture

### Hybrid retrieval

A query like *"what's happening with Ethereum?"* needs two different kinds of lookup:

1. **Semantic search** — finding text that's relevant in meaning (news articles, coin descriptions), via vector similarity search (pgvector, cosine distance)
2. **Structured lookup** — finding the exact current price, which vector search can't do reliably (embeddings capture meaning, not precise numbers)

The system runs both and combines them. This combination happens in one deliberately narrow module (`hybrid_retriever.py`) — the only place in the codebase that translates between this project's generic data model and the pipeline's coin-specific one (see "Generic core, domain-specific adapter" below).

### Pipeline

```
Ingestion → Chunking → Embedding → Storage → Retrieval → Generation
```

| Stage | What happens | Key files |
|---|---|---|
| Ingestion | Pull news (RSS) and coin descriptions (read from pipeline's DB) | `rag_src/ingestion/` |
| Chunking | Split long text into overlapping ~400-token pieces | `rag_src/embedding/chunker.py` |
| Embedding | Convert each chunk into a 768-dim vector (Ollama, `nomic-embed-text`) | `rag_src/embedding/embedder.py` |
| Storage | Save chunks + vectors to Postgres (pgvector), upsert-safe | `rag_src/embedding/indexer.py` |
| Retrieval | Vector search + structured price lookup, combined | `rag_src/retrieval/` |
| Generation | LLM (Llama 3.1 8B, local via Ollama) writes the answer, constrained to structured JSON output | `rag_src/generation/` |

### Key design decisions

- **Generic core, domain-specific adapter.** Nothing in `ingestion/`, `embedding/`, or `retrieval/vector_search.py` knows what a "coin" is — everything is expressed in terms of a generic `entity_id`/`entity_type`. Only `hybrid_retriever.py` translates a generic `entity_id` into the pipeline's `coin_id` to join against price data. This keeps the core reusable for other domains later, and keeps the coupling to the legacy schema contained to one file.
- **Numbers from SQL, narrative from LLM.** Every numeric field in a response (`top_movers`, prices) is computed in SQL before the LLM ever runs. The LLM is asked only for the parts that genuinely need language generation (summary, sentiment), via a narrower internal schema — never for the full response shape.
- **Structured output, not free text.** The LLM's output is constrained to match a JSON schema (via Ollama's `format` parameter), generated from the same Pydantic models (`RAGResponse`, `DailyReportResponse`) used everywhere else in the codebase.
- **Own Airflow instance, not a shared one.** See "How it relates to crypto-market-pipeline" above.

## Tech stack

| Layer | Choice | Why |
|---|---|---|
| Vector store | PostgreSQL + pgvector | Reuses existing infrastructure, no new database to run |
| Embedding model | `nomic-embed-text` (Ollama, local) | Free, runs on CPU, no API costs during development |
| Chat model | `llama3.1:8b` (Ollama, local) | Verified to fit available RAM (~9.6GB) on a laptop with no discrete GPU; `Mistral Small 3.2` (~12GB) was ruled out for this reason |
| Orchestration | Apache Airflow (TaskFlow API) | Consistent with `crypto-market-pipeline`'s existing tooling |
| Schema validation | Pydantic v2 | Used for both data contracts (`RawDocument`) and structured LLM output |
| CLI | Typer + Rich | Manual query/report interface for Fase 1 |
| Testing | pytest + pytest-mock | 42 tests, 99% coverage on `rag_src/` |

## Project structure

```
crypto-market-rag/
├── rag_src/
│   ├── schemas/        # Pydantic contracts (RawDocument, RAGResponse, DailyReportResponse)
│   ├── ingestion/       # News RSS + coin descriptions (read-only from pipeline's DB)
│   ├── embedding/       # Chunking, embedding, storage
│   ├── retrieval/       # Vector search (generic) + hybrid retriever (adapter)
│   ├── generation/      # LLM client, report generator, query answerer
│   ├── cli/             # Terminal entry point
│   └── utils/           # Config, logging, observability
├── dags/                 # Airflow DAGs (news ingestion, daily report)
├── sql/                  # Database schema (pgvector setup, rag_user permissions)
├── tests/                 # pytest suite
├── Dockerfile             # This project's own Airflow image
└── docker-compose.yml     # This project's own Airflow instance
```

> Note: the package is named `rag_src`, not `src` — `crypto-market-pipeline`'s own Airflow container mounts a `src/` folder of its own, and using the same top-level package name in both would risk Python resolving imports to the wrong project's code if the two were ever run in the same process. This is documented as a decision, not an accident.

## Setup

### Prerequisites

- Python 3.11+, [Poetry](https://python-poetry.org/)
- [Ollama](https://ollama.com/), running locally with `nomic-embed-text` and `llama3.1:8b` pulled
- Docker + Docker Compose
- `crypto-market-pipeline` already running (this project reads from its database)

### Local development

```bash
poetry install
cp .env.example .env   # fill in POSTGRES_* and OLLAMA_* values
poetry run python -m pytest -v   # verify everything works
```

### Running the CLI

```bash
poetry run python -m rag_src.cli.main query "how is bitcoin doing today"
poetry run python -m rag_src.cli.main report
```

### Running the scheduled pipeline (Airflow)

```bash
docker compose build
docker compose up -d
```

Airflow UI at `http://localhost:8081` (separate from `crypto-market-pipeline`'s, at `:8080`). Requires `crypto-market-pipeline` to already be running first, so the shared Docker network (`crypto_shared_net`) exists.

---

## Known limitations

- **Ollama's default rate limit** is under 10 requests/second — fine for single-user/portfolio use, but a real constraint if this were ever exposed to multiple concurrent users. Upgrade path: [vLLM](https://github.com/vllm-project/vllm) for production-grade serving.
- **CPU-only inference.** No discrete GPU on the development machine means generation takes longer (tens of seconds per query) than it would with GPU acceleration.
- **RSS-only news ingestion.** No paid news API is used, so coverage depends on what CoinTelegraph's public feed includes.

## Roadmap

**Fase 1 (complete):** the full pipeline above — ingestion, embedding, retrieval, generation, CLI, scheduled automation via Airflow.

**Fase 2 (planned):** an interactive Telegram bot, reusing `rag_src/generation/` directly (no logic duplication — the bot is a thin interface over the same `answer_query()`/`generate_daily_report()` functions the CLI uses). A web app was considered and deliberately deprioritized in favor of the bot, as a better effort-to-value trade-off for this project's current scope.
